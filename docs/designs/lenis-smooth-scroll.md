## Problem Statement
The site's scroll-triggered entrance animations (`useRiseReveal.ts`'s GSAP ScrollTrigger system, applied via `.rise-soft`/`.rise-card` across every section) all use the same rise+fade choreography. After a long session tuning and debugging one instance of it (`.wall-frame-in` on My Portfolio's wall-frame), the user is bored of the current feel and wants scroll animation to feel different — not a bug fix, a taste/aesthetic refresh.

## What Makes This Cool
Swapping the scroll *feel* itself (inertial, weighted, "sticks to your finger") is a bigger, more felt change than re-skinning individual reveal animations. It's the same trick that makes Awwwards-tier sites feel expensive: the whole page moves differently, not just the elements on it.

## Constraints
- Must not break the two working, recently-fixed systems: `useRiseReveal.ts`'s GSAP ScrollTrigger reveals (used site-wide) and the newly-fixed `.wall-frame-in` reveal on `PortfolioSection.tsx`.
- Must not break `window.scrollY`-dependent code: `ContactSection.tsx`, `Navbar.tsx`, `PortfolioSection.tsx` (`lockWallGeometry`, wall notch/clip-path math), `utils/navHeader.ts`.
- Must not break the 17 `position: fixed`/`sticky` CSS declarations (notably the fixed navbar).
- Solo-maintained personal portfolio — no team coordination cost, but also no one else to catch regressions; the user is the only QA.

## Premises
1. The actual trigger for this conversation was a specific reveal animation (`.wall-frame-in`) not firing — confirmed via source inspection to be correctly implemented (CSS/JS served correctly by dev server; other `.rise-soft`/`.rise-card` reveals confirmed working by the user). — **User note: superseded — the real motivation is broader aesthetic fatigue with the scroll feel, not that specific bug.**
2. Locomotive Scroll v5's `data-scroll-class` in-view detection cannot be adopted standalone — it requires taking on its Lenis-based smooth-scroll behavior site-wide. — Agreed.
3. The codebase has real native-scroll coupling: 4 files read `window.scrollY` directly, 8 use raw `IntersectionObserver`, 4 use GSAP ScrollTrigger, 17 CSS declarations use `position: fixed`/`sticky`. — Agreed, informed scope sizing.
4. The existing reveal system already works reliably (confirmed by the user across every section except the one bug just fixed) — a full Locomotive Scroll migration is not needed to get reliable reveal-on-view. — Agreed, but the actual goal shifted from "fix reliability" to "change the feel," which reframes the recommended approach (see below).

## Approaches Considered
### Approach A: Reveal choreography refresh only (no new dependency)
Keep native scroll. Vary `useRiseReveal.ts`'s reveal language per section (clip-path wipes, scale-in, letter-stagger) instead of one uniform rise+fade everywhere.
- Effort: S, Risk: Low, zero new dependencies.

### Approach B: Adopt Lenis (standalone) wired into existing GSAP ScrollTrigger — RECOMMENDED
Add `lenis` (~5kb), not the full `locomotive-scroll` package. Lenis intercepts wheel/touch input and smooths the *real* `window.scrollTo` position per Lenis's own README (not a virtual/hijacked scrollbar in its default mode — this claim is read-verified against the library's docs, but NOT yet verified against this repo's own complex geometry-locking system; treat as a working assumption to confirm in Next Steps step 2, not a settled fact). GSAP's official integration is 4 lines (`lenis.on('scroll', ScrollTrigger.update)`, `gsap.ticker.add(...)`, `gsap.ticker.lagSmoothing(0)`). This changes the actual felt scroll physics on the homepage — the thing the user says they're bored of — while every existing `.rise-soft`/`.rise-card`/`.wall-frame-in` reveal keeps working largely unchanged, because they still read real scroll/viewport position under the hood.
- Effort: **L** (revised up from M during /plan-eng-review's outside-voice pass — see Open Questions). One new ~5kb dependency.
- Risk: Medium. Three separate places *write* to `window.scrollTo` and will fight Lenis for control of scroll position unless rewritten to drive Lenis's own target instead (see Open Questions) — this is now core scope, not a follow-up.
- Rollback is **not** a clean single-commit revert once `navHeader.ts`'s `animateScrollTo` is rewritten to route through Lenis — that rewrite has to be reverted together with the Lenis init, and `navHeader.ts` is the site's only nav-click scroll mechanism, so test the revert path too, don't assume it.

### Approach C: Full `useRiseReveal.ts` redesign, no new dependency
Keep native scroll entirely; redesign the reveal system's core spring/stagger language from scratch to replace the current rise+fade everywhere.
- Effort: L, Risk: Low (no new dependency), but the largest surface-area change (rewrites the shared reveal engine every section depends on).

## Recommended Approach
**Approach B**, reaffirmed after /plan-eng-review's outside-voice pass raised a legitimate strategic tension: the confirmed trigger was aesthetic fatigue with the reveal animation, not a scroll-physics complaint, and Approach A (zero new dependency, directly targets "the reveal looks the same everywhere") is the lower-risk answer to that literal problem. The user considered this and chose to stay on B anyway, wanting the bigger felt change over the safer one — a taste call, made with the full cost now on the table (three scroll-writing call sites need rewriting, not one line each).

Approaches A and C only restyle reveal-on-enter animations; neither touches the scroll motion itself, which is what the user actually said they're tired of.

## Open Questions
- **[CRITICAL, found by outside-voice review, not the initial pass]** Three places *write* to `window.scrollTo` and will fight Lenis's internal smoothing target unless rewritten to drive Lenis itself:
  - [navHeader.ts:104,151,157-158](src/utils/navHeader.ts:104) `animateScrollTo` — a hand-rolled, self-correcting per-frame rAF tween that is the *only* scroll mechanism behind every nav click/hash link on the site. This needs to become a driver of Lenis's target position, not a second competing loop calling `window.scrollTo` directly.
  - [ContactSection.tsx:307](src/components/ContactSection.tsx:307) — back-to-top button, native `behavior:'smooth'`. Native smooth-scroll conflicting with Lenis is a documented footgun; switch this call to `lenis.scrollTo()`.
  - [PortfolioSection.tsx:881,1099](src/components/PortfolioSection.tsx:881) — scroll-position restore-on-return and expand/collapse scroll jumps, both `behavior:'instant'`. Concrete failure scenario: leave a project page, hit back — if Lenis already cached the pre-navigation scroll position into its own internal target before this restore runs, Lenis's next smoothing tick can silently scroll the page back to its old (wrong) position, undoing the restore. This path is not exercised by casual manual testing (only "leave a project page, then back") so it needs an explicit test, not just eyeballing.
- Does `lockWallGeometry` in `PortfolioSection.tsx` (reads `frame.style.top`/measures on `window.scrollY`-adjacent timing) stay correct once scroll position updates are smoothed/delayed by a frame or two, rather than synchronous with input? Needs a manual test pass, not just static analysis. **Fallback if it drifts:** read Lenis's own `scroll`/`velocity` event payload (or its raw, pre-smoothing input) for that one measurement instead of `window.scrollY`, rather than reworking the geometry-lock logic itself.
- Does the fixed navbar's own scroll-position-based show/hide or style-change logic (`Navbar.tsx`) read `window.scrollY` per-frame or per-scroll-event — either should keep working, but confirm no assumption of synchronous same-tick scroll delta.
- iOS Safari touch behavior needs real-device testing before shipping — this project has a documented prior incident with touch-device scroll heuristics misfiring on Windows touch+mouse hybrids (see `pointer:coarse` fix history); Lenis + iOS inertial touch scrolling is a commonly-reported rough edge for this class of library and deserves the same scrutiny.
- `prefers-reduced-motion` visitors should bypass Lenis's smoothing entirely (gate the `new Lenis()` call itself, not just the GSAP reveal side, which already handles it) — inertial scroll motion is exactly the kind of effect that setting exists to suppress.
- RAF-loop stacking: the marquee auto-scroll, MagicBento cursor tracking, `navHeader.ts`'s tween, and GSAP's ScrollTrigger ticker already run concurrently; Lenis adds one more loop and takes over `lagSmoothing(0)`. No pre-implementation frame-budget estimate exists — this is deferred to real-device testing in Next Steps rather than estimated up front, which means a jank issue found late could take real effort to isolate which loop is responsible.
- Tune Lenis's `lerp`/`duration` to taste — this is a feel decision the user should test live, not something to pre-decide in the design doc.

## Success Criteria
- Scrolling anywhere on the site feels inertial/weighted instead of the current native 1:1 scroll.
- All existing entrance reveals (`.rise-soft`, `.rise-card`, `.wall-frame-in`) still fire correctly and visibly.
- `PortfolioSection.tsx`'s wall geometry lock, the fixed navbar, `ContactSection.tsx`, and anchor/hash navigation show no regressions.
- Scroll stays smooth on a real mid-range device — no visible jank/dropped frames during the marquee wall's scroll or while GSAP reveals are actively animating.
- `prefers-reduced-motion` visitors get native, non-smoothed scroll (Lenis skipped entirely for them).
- No new console errors; `npm test` and `tsc --noEmit` stay green (pre-existing unrelated failures on this branch excluded).
